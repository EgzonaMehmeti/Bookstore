Bookstore API

A .NET 9 REST API for managing books and authors, with SQL Server persistence, OAuth 2.0 authentication through Duende IdentityServer, Swagger UI testing, and Docker support.

Solution Structure
Bookstore
├── BookstoreApi
└── IdentityServer
BookstoreApi

The main REST API responsible for:

Book CRUD operations
Book search by title and author
Pagination
SQL Server persistence using Entity Framework Core
OAuth 2.0 access token validation
Swagger UI for API testing
IdentityServer

A Duende IdentityServer application responsible for issuing OAuth 2.0 access tokens for the Bookstore API.

Two OAuth 2.0 flows are configured:

Client Credentials for Book CRUD
Implicit Flow for Book Search

Running the Application
1. Configure the database

The API uses SQL Server LocalDB by default.

The connection string is located in:

BookstoreApi/appsettings.json

Default configuration:

"ConnectionStrings": {
  "DefaultConnection": "Server=(localdb)\\MSSQLLocalDB;Database=BookstoreDb;Trusted_Connection=True;TrustServerCertificate=True;MultipleActiveResultSets=true"
}

If a different SQL Server instance is required, update DefaultConnection accordingly.

2. Apply database migrations

Open the Visual Studio Package Manager Console and select BookstoreApi as the Default Project.

Run:

Update-Database

This creates the BookstoreDb database and applies the existing Entity Framework Core migrations.

3. Start IdentityServer

Start the IdentityServer project first.

The development configuration uses HTTPS.

The OAuth authority used by the API is configured in:

BookstoreApi/appsettings.json

Example:

"Authentication": {
  "Authority": "https://localhost:44303",
  "Audience": "bookstore-api"
}

The exact HTTPS port may differ depending on the local IIS Express configuration.

IdentityServer exposes the standard OpenID Connect discovery endpoint:

/.well-known/openid-configuration
4. Start BookstoreApi

Start BookstoreApi using the HTTPS / IIS Express profile configured in Visual Studio.

Swagger UI is available at:

https://localhost:44302/swagger

The exact port may differ depending on the local IIS Express configuration.

Validation and Business Rules

The API validates the requirements defined by the object model.

Author
authorId is generated by the database
name is required
name must contain between 3 and 100 characters
Author names are unique
Book
bookId is generated by the database
author is required
title is required
title must contain between 3 and 100 characters
subTitle is optional
An author cannot have two books with the same title

The database also enforces the relevant keys, relationships, indexes, and uniqueness constraints.

Architecture

The API follows a layered architecture:

Controller
    ↓
Service
    ↓
Repository
    ↓
DbContext
    ↓
SQL Server
Controllers

Handle HTTP requests and return HTTP responses.

Services

Contain business logic, validation, DTO mapping, and application rules.

Repositories

Handle database access through Entity Framework Core.

DbContext

Provides access to SQL Server and manages Entity Framework Core entities and configurations.

DTOs

Separate API request/response models from database entities.

Authentication and Authorization

The API validates JWT access tokens issued by Duende IdentityServer.

Authorization is implemented using policies:

BooksPolicy
    → requires bookstore.books scope

SearchPolicy
    → requires bookstore.search scope

This ensures that possessing a valid token alone is not sufficient; the token must also contain the required scope for the requested operation.

Test Credentials and Security Note

The credentials included in this repository are development/test credentials intentionally provided to make the coding assignment easy to run and evaluate locally.

For example:

Client ID: bookstore-crud-client
Client Secret: bookstore-secret

Username: testuser
Password: test123

These credentials and the in-memory test user configuration must not be used in a production environment.

A production implementation should instead:

Store secrets outside the source code
Use environment variables, a secrets manager, or equivalent secure configuration
Store users in a proper persistent identity/user store
Use secure password hashing and user management
Avoid hard-coded client secrets and passwords
Use production signing certificates/keys instead of development signing credentials
Configure appropriate HTTPS certificates and trusted infrastructure
Apply appropriate token expiration, rotation, and security policies

The current configuration is intentionally simplified for local development and technical-assignment evaluation.

Error Handling

The API includes centralized exception handling middleware.

Known business conflicts return:

409 Conflict

Unexpected server errors return:

500 Internal Server Error

The API avoids exposing internal exception details to clients.
